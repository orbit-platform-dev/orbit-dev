# Orbit — バックエンド・エージェントアーキテクチャ

Orbit のバックエンドがどのように動くのかを、簡潔かつ網羅的に説明します。
顧客との会話が、Orbit がその顧客についてすでに知っているすべての情報と組み合わさり、
レビュー・承認・同期された一連の社内アップデートになるまでの流れです。

---

## 1. バックエンドの役割

Orbit は**実行プラットフォーム**です — 顧客との会話と会社の実行のあいだに立つ
**レビューと承認のレイヤー**。バックエンドは**会議のトランスクリプト**を受け取り、
その背後にいる**顧客**を特定し、その顧客の**履歴**を取得したうえで、完全な
**実行プラン**を用意します:CRM 更新の提案、PRD(オンデマンド生成)、チーム別の
作業項目、タイムライン、顧客向けフォローアップ — これらが**実行グラフ**で接続され、
すべての成果物が「*なぜ存在するのか*」を説明します。

**何も自動では実行されません。** 人間がすべてのドラフトをレビュー・編集し、
プランを承認(=ロック)し、各アップデートを**明示的に**プッシュします — Jira、
Notion、CRM、メールへ。これらの既存ツールが**システム・オブ・レコード**であり
続けます。承認された出力だけが顧客の恒久的な**ナレッジ**となり、次の会議の提案を
より賢くします。

**技術スタック:** FastAPI (async) · LangGraph (エージェント編成) · PydanticAI
(型付き LLM ラッパー) · SQLAlchemy 2 (async) · PostgreSQL + **pgvector** /
SQLite · **Alembic** (マイグレーション) · Redis (任意) · Docker

## 2. レイヤー構成

```
┌──────────────────────────────────────────────────────────────┐
│  HTTP レイヤー      FastAPI + 14 の REST ルーター               │
│                    meetings · customers · chat · calendar ·   │
│                    zoom · meet · projects · tasks · graph ·   │
│                    timeline · integrations · activity · …     │
├──────────────────────────────────────────────────────────────┤
│  コンテキスト       生成 1 回につき 1 つの構造化された           │
│  エンジン ★        ContextPackage:SQL の事実 + pgvector に    │
│                    よる顧客履歴のセマンティック検索              │
├──────────────────────────────────────────────────────────────┤
│  エージェント ★    型付き PydanticAI エージェント 10 体の       │
│  レイヤー          LangGraph パイプライン + プロバイダー非依存   │
│                    のモデルサービス                             │
├──────────────────────────────────────────────────────────────┤
│  サービス          customers (顧客同定) · knowledge (承認済み   │
│                    の真実) · sync (準備されたジョブ) ·          │
│                    embeddings · workspace (テナンシー)         │
├──────────────────────────────────────────────────────────────┤
│  永続化            エージェント出力 → ExecutionPlan・グラフ・    │
│                    タスク(会議ごとに冪等)                      │
├──────────────────────────────────────────────────────────────┤
│  データ / インフラ  Async SQLAlchemy · Alembic (起動時に自動     │
│                    適用) · Postgres+pgvector / SQLite ·        │
│                    Redis (任意) · Clerk 認証 · 設定             │
└──────────────────────────────────────────────────────────────┘
```

★ の 2 レイヤーがプロダクトの核心です。**コンテキストエンジン**が「生成時に
どの履歴を見せるか」を決め、**エージェント**がトランスクリプト + コンテキストを
提案に変えます。

## 3. エンドツーエンドの流れ

```
POST /meetings/transcript  { transcript, title, account }
   │
   ▼
[顧客を特定]     resolve_customer():正規化した名前 → エイリアス → メール
   │            ドメイン。「acme」も「Acme Inc」も同じ Customer に着地
   ▼
[履歴を取得]     build_context_package(customer, wide=True):
   │            セマンティックに一致した過去の会議 + 承認済みプラン +
   │            未完了コミットメント + 承認済みナレッジ → 1 つのテキスト
   ▼
[パイプライン]   10 エージェント(LangGraph)。全員が同じコンテキストを見る —
   │            シグナル → PRD 下書き → ルーター → crm ∥ eng ∥ design →
   │            qa・sales → 作業項目 + タイムライン → フォローアップメール
   ▼
[永続化]        ExecutionPlan(ドラフト)+ グラフ + タスク。会議は将来の
   │            セマンティック検索用に埋め込み化。PRD はまだ保存されない —
   ▼            レビュー画面でオンデマンド生成(§6)
[レビュー]      すべてのセクションが編集可能なドラフト。Generate PRD ボタン。
   │            まだ何も Orbit の外に出ていない
   ▼
[承認]          一度の操作で 4 つの効果 — ただし実行はゼロ:
   │              1. プランがロック(以後の編集は全て 409、UI も追従)
   │              2. Approval 監査行(誰が・いつ・どのセクションを)
   │              3. 承認済みセクション → KnowledgeItem(+ コミットメント)
   │              4. SyncJob を準備(status: pending)
   ▼
[同期 — 明示的]  各セクションのプッシュボタンがジョブを 1 つずつ実行:
   │            PRD→Notion · Issue→Jira · CRM 更新 · メール送信
   ▼            (接続先が未接続なら、ジョブが理由を説明して skipped)
[記憶]          ナレッジ + 埋め込みが「次の」会議のコンテキストになる
```

再分析は**冪等**です:永続化は新しい行を書く前に、その会議の古いプラン/グラフ/
タスクを削除します。

## 4. コンテキストエンジン (`app/context/engine.py`)

履歴への唯一の入口。すべての生成器 — パイプライン全体とチャット — が同じ構造化
された `ContextPackage` を消費します。生のテーブルやトランスクリプトを LLM に
渡すことは決してありません。

**ハイブリッド検索:**

| データ | 取得方法 | 理由 |
|---|---|---|
| 未完了コミットメント・承認済みプラン・プロフィール | 素の SQL(インデックス付き) | 正確な事実 — 「似ている」ではなく「すべて」が必要 |
| 「N 件の過去会議のうち、*いま*重要なのはどれか」 | 埋め込みに対する **pgvector** コサイン検索 | 意味ベース:「ログインの問題」が「SAML アサーションエラー」の会議を見つける |
| 承認済みナレッジ(PRD・CRM 更新・メール) | 同じく pgvector、新しさで補完 | 同上 |

**埋め込み** (`services/embeddings.py`):Gemini `gemini-embedding-001`、768
次元。会議の分析時とナレッジの承認時に書き込み(+ 起動時に上限付きバックフィル)。
Postgres では本物の `vector` カラム + HNSW インデックス(マイグレーション 0003、
compose の db イメージは `pgvector/pgvector:pg16`)— 顧客あたり数千件の会議でも
類似検索は高速のまま。開発用 SQLite では同じ値を JSON として保持し Python 側の
コサインでランク付け。埋め込みが一切ない場合(AI オフ)はキーワード一致 + 新しさに
フォールバック。検索が壊れることはありません。

**上限**がプロンプトを軽く保ちます:パイプラインとチャットは *wide* セット
(会議 12・プラン 8・コミットメント 20・ナレッジ 15)を使い、すべての文字列を
切り詰めます。コンテキストは多ければ良いのではなく — セマンティックランキングが
その枠を「正しい履歴」で埋めることに意味があります。

## 5. エージェントシステム

### 5.1 エージェントとは

1. **システムプロンプト** — プロフェッショナルなペルソナ(「*一流エンタープライズ
   SaaS のシニア PM として書け…*」)。実務フォーマットを要求します:
   Given/When/Then の受け入れ基準、標準的な CRM ステージ、プレースホルダーの
   ないメール。
2. **型付き出力スキーマ** — 制約付きデコーディング(`NativeOutput`)で強制される
   Pydantic モデル。検証失敗は ×3 リトライ。出力は camelCase にシリアライズされ、
   そのままフロントエンドに落ちます。
3. **モデル** — プロバイダー非依存のモデルサービスから供給。

### 5.2 モデルサービス

`DEFAULT_MODEL = "provider:name"` がレジストリ(`google-gla`, `google`,
`ollama`, `anthropic`, `openai`)に解決されます。プロバイダーの切り替えは環境
変数の変更だけ。追加はレジストリ 1 エントリです。

| ユースケース | DEFAULT_MODEL | 必要なキー |
| --- | --- | --- |
| 無料の開発 | `google-gla:gemini-flash-lite-latest` | Gemini キー |
| ローカル / オフライン | `ollama:llama3.1` | なし |
| 本番 | `anthropic:claude-opus-4-8` | Anthropic キー |

### 5.3 10 のエージェント

| # | エージェント | 入力 | 出力 |
|---|---|---|---|
| 1 | `meeting-intelligence` | トランスクリプト **+ コンテキスト** | シグナル:要約・感情・緊急度・ペイン・要望・期限・売上影響 |
| 2 | `product-manager` | シグナル **+ コンテキスト** | PRD ドラフト(パイプライン中は内部用。保存される PRD はユーザー操作で生成) |
| 3 | `execution-router` ★ | シグナル + PRD **+ コンテキスト** | **この会議に必要なセクションと理由**(crm・eng・design・qa・sales・cs) |
| 4 | `crm-analyst` | シグナル **+ コンテキスト** | CRM 更新提案:アカウント要約・ステージ・リスク・根拠付きフィールド更新 |
| 5 | `engineering-planner` | PRD **+ コンテキスト** | アーキテクチャ・コンポーネント・見積り・リスク |
| 6 | `design-planner` | PRD **+ コンテキスト** | フロー・画面 |
| 7 | `qa-planner` | PRD + エンジニアリング **+ コンテキスト** | テスト戦略・ケース・カバレッジ |
| 8 | `sales-planner` | PRD **+ コンテキスト** | ポジショニング・トークトラック・セグメント |
| 9 | `execution-planner` | PRD + シグナル + ルーティング **+ コンテキスト** | チーム横断の作業項目(各項目に WHY)。タイムラインは決定論的に導出 |
| 10 | `customer-success` | シグナル + アカウント **+ コンテキスト** | フォローアップメール + コミットメント |

加えて `orbit-chat`(コンテキストパッケージ上で質問に回答 — §8)と
`leadership-advisor`(定義済み・未接続)。

**すべてのエージェントが同じレンダリング済みコンテキストを受け取ります** —
過去の要望、承認済みプラン、未完了コミットメント — そして指示されます:履歴を
参照せよ、提供済みのものを再提案するな、繰り返されるテーマを指摘せよ。単一の
会議だけからアップデートが起案されることはありません。

### 5.4 LangGraph パイプライン

```
        トランスクリプト + ContextPackage
                      │
          meeting-intelligence → シグナル
                      │
              product-manager → PRD(内部用)
                      │
            execution-router ★ → セクション {relevant, reason}
            ╱         │         ╲              (ファンアウト)
     crm-analyst  engineering  design   ← ルーターが不要と判断した
            ╲         │  ╲       │         ノードは自らスキップ
             ╲        │   ╲      ▼
              ╲       │    ╲    qa   (eng + design を待つ)
               ╲      │    sales
                ╲     ▼     ╱
              execution-planner → 作業項目 + タイムライン
                      │
              customer-success → フォローアップメール
```

ノードは**部分的な状態更新**(自分が生成したキーのみ)を返し、共有の `events`
はリデューサーチャネル(`operator.add`)です — これが 3 並列ブランチを安全に
します。ノードが状態全体を返すと LangGraph の `InvalidUpdateError` になります。

### 5.5 実行ルーター

すべての会話にすべてのセクションが必要なわけではありません:価格に関する苦情に
QA は不要。サポートのエスカレーションに CRM ステージ変更は不要かもしれない。
ルーターはセクションごとに一行の理由付きで判断し、スキップされたセクションは
何も生成せず、グラフに `skipped` として — 理由とともに — 表示されます。

### 5.6 グレースフルデグラデーション

すべてのエージェント呼び出しは、LLM の失敗時に決定論的な(トランスクリプト由来の)
フォールバック関数に落ちます。`ENABLE_AI=false` ならプロダクト全体がオフラインで
動作。LangGraph 自体が使えなければ同じノードを逐次実行。埋め込みの失敗は検索を
キーワードランキングに落とすだけ。パイプラインがリクエストを壊すことはなく、
失敗した分析は会議を `failed` にします(回り続けるスピナーにはなりません)。

## 6. エージェント出力からレビュー画面へ

永続化(`agents/persistence.py`)は会議ごとに書き込みます:

- **ExecutionPlan**(テーブルは `projects`。`Project` は互換エイリアス)—
  中心となるビジネスオブジェクト:`crm_update`・`engineering`・`design`・`qa`・
  `sales`・`customer_update`・`timeline`・`internal_notes` の JSON セクション、
  `approval_status`、`customer_id`、`workspace_id`。**`prd` は空で始まります** —
  レビュー画面の *Generate PRD* ボタン(`POST /projects/{id}/generate-prd`)が、
  「現在の(人間が編集したかもしれない)インテント + コンテキストパッケージ」から
  オンデマンドで生成します。人間が求めるまで PRD は存在しません。
- **グラフのノード/エッジ** — Meeting → Intent → CRM Update → PRD → Plan →
  {Eng, Design, Sales} → QA → Timeline → Email → **Synchronization**。ID は
  会議ごと(`g_{meetingId}_{kind}`)。すべてのノードが「なぜ」を保持
  (`meta.reason`)。Sync ノードはプッシュ完了まで `pending`。
- **タスク** — 全職種にまたがる作業項目。各項目が理由と確信度を持ちます。
- フォローアップメールの**宛先は自動割り当て**(顧客に学習済みの
  `Customer.meta.contactEmail`)され、編集可能な「To」欄として表示されます。

シグナルガードが雑談を除外します:実際のフィーチャー要望かペインポイントの
ある会議だけがプランを生みます。

## 7. 承認 → ナレッジ → 同期

`POST /meetings/{id}/approve` は**ロックと準備だけを行い、決して実行しません**:

1. **ロック** — プランの PATCH、会議分析の PATCH、タスクの全編集
   (アサイン/却下/削除を含む)が 409 を返します。かんばんの列移動だけは開いた
   まま(それはプラン編集ではなく進行管理だから)。
2. **監査** — `Approval` 行が「誰が・どのセクションを・いつ」承認したかを記録。
3. **ナレッジ** — `services/knowledge.py` が承認済みセクションを
   `KnowledgeItem` にスナップショット:会議要約・CRM 更新・PRD・タイムライン・
   メール、そして各コミットメントを個別の「未完了」項目として。**承認された
   出力だけがナレッジになります — 生の AI 出力が真実として保存されることは
   ありません。** 項目はセマンティック検索用に埋め込み化されます。
4. **SyncJob の準備** — 承認されたセクションごとに pending なジョブを 1 つ
   (`crm-update`・`publish-prd`・`create-tasks`・`send-email`)。接続先が
   なければジョブは人間が読める理由付きで `skipped`。

**実行は別個の、人間の行為です**:各セクションのプッシュボタンが
`POST /projects/{id}/sync-jobs/{job}/run` を呼びます(メール送信は宛先必須。
送信すると宛先が Customer に学習されます)。`services/sync.py` の実行器が
実 API を差し込む継ぎ目で — 現在はスタブのリンクですが、監査されたジョブ
パイプライン(status / result / error / リトライ)を通ります。最後のジョブが
終わると、グラフの Synchronization ノードが完了します。

## 8. 顧客・チャット・履歴

- **顧客同定** (`services/customers.py`):会議のアカウントラベルを実在の
  `Customer` に解決(正規化名 → エイリアス → メールドメイン。「Inc」等の接尾辞は
  無視)。汎用的なラベルは推測せずに未リンクのまま。顧客は直接作成も可能
  (`POST /customers`)。
- **チャット** (`routers/chat.py`):会話は**永続化**されます
  (`chat_conversations`)— Claude/GPT のチャットのように。各会話が
  トランスクリプトと顧客バインディングを保持。顧客検出はファジー
  (「nortwind」→ Northwind Labs。曖昧なら推測せずに聞き返す)。すべての回答は
  *wide* な ContextPackage に接地。AI オフ時は決定論的なコンテキスト由来の回答。
  履歴 API:`GET/DELETE /chat/conversations[/{id}]`。

## 9. データモデル

16 テーブル(JSON リッチ)。すべてのビジネス行が `workspace_id` を持ちます:

```
Workspace ─── Customer ──┬─► Meeting (embedding) ──► ExecutionPlan (projects)
                         │        │                     ├─► GraphNode ─► GraphEdge
                         │        ├─► TimelineEvent     ├─► Task
                         │        └─► ActivityEvent     ├─► Approval
                         ├─► KnowledgeItem (embedding)  └─► SyncJob
                         └─► ChatConversation
Member · Agent · Integration · CalendarConnection   (補助データ)
```

**マイグレーションは Alembic**(`backend/alembic/`)で、起動時に自動適用されます:
新規 DB → create_all + stamp head。Alembic 以前の DB → baseline を stamp して
upgrade(+ 古い開発 DB のドリフト補修)。管理下の DB → upgrade。スキーマ変更は
必ずマイグレーションで — モデルの編集だけでは反映されません。

## 10. 周辺インフラ

- **取り込み** — トランスクリプトの貼り付け、**Zoom**(OAuth → クラウド録画の
  VTT インポート)、**Google Meet**(OAuth → Meet REST API のトランスクリプト
  *エントリー*)。Google カレンダーは**読み取り専用**のスケジュール同期。
  Orbit 自体は文字起こしを行いません。
- **Redis** — 任意のイベントストリーム。未設定なら no-op。
- **認証 / テナンシー** — Clerk JWT(開発では無効 → デモプリンシパル)。
  `services/workspace.py` が org クレームをワークスペースにマップ
  (開発では `ws_default`)。
- **設定** — `.env` からの単一の settings オブジェクト。何も設定しなくても
  アプリはグレースフルに動作します。

## 11. すべての判断を説明する原則

1. **Orbit は提案し、人間が承認し、既存ツールがシステム・オブ・レコードで
   あり続ける。** 承認はロックであり、実行ではない。外向きのアップデートは
   すべて明示的で監査された人間の行為。
2. **承認された出力だけがナレッジになる** — そしてナレッジは(顧客ごとに
   セマンティックに検索されて)将来のすべての生成に供給される。ループは複利で
   効いていく。
3. **コンテキストエンジンはひとつ** — すべての生成器とチャットに対して、
   上限付き・ハイブリッド検索の単一パッケージ。データベースをプロンプトに
   流し込まない。
4. **プロバイダー非依存 + グレースフルデグラデーション** — LLM は環境変数で
   交換。LLM がなくてもプロダクトは動く。
5. **グラフこそがプロダクト** — 実在する成果物、実在する関係、「何が必要か」を
   推論するルーター、すべてのノードに「なぜ」。

> **一文でいえば:** トランスクリプトが入ると、Orbit は顧客を特定し、単一の
> コンテキストエンジン(SQL の事実 + pgvector のセマンティック検索)で履歴を
> 取得し、型付きエージェント 10 体の LangGraph パイプラインが実行パッケージ全体を
> 起案し、人間が編集して承認し(それがロックと監査と顧客ナレッジ化を意味し)、
> 各アップデートはシステム・オブ・レコードであり続けるツールへ明示的に
> プッシュされ — 承認されたすべてが次の会話を賢くします。
